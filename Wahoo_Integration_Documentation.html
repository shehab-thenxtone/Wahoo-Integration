2. Integration Know-How (10-Step Implementation Flow)

1

Create App & Obtain Credentials

Goal: Create a Cloud API app, obtain OAuth credentials, authorize users, and call Wahoo endpoints.

  1. Create a developer account

    Go to developers.wahooligan.com and sign in with your Wahoo account.

  2. Create a new application

    Open My Developer Apps → Create App → enter App Name, Description, Redirect URI, and select scopes.

    ⚠ Gated Access: Wahoo manually reviews all applications. New apps start in sandbox mode (250 req/day). Production access requires explicit approval — there is no self-serve upgrade.

  3. Obtain Client ID and Client Secret

    After creation the Developer Portal shows Client ID, Client Secret, and Redirect URI. See cloud-api.wahooligan.com.

  4. Implement OAuth 2.0

    https://api.wahooligan.com/oauth/authorize?
client_id=YOUR_CLIENT_ID
&redirect_uri=YOUR_REDIRECT_URI
&scope=user_read workouts_read offline_data
&response_type=code
    PKCE: For public/non-confidential apps, Wahoo also supports the PKCE OAuth flow.

  5. Exchange authorization code for tokens

    POST https://api.wahooligan.com/oauth/token
{
  "client_id": "...",
  "client_secret": "...",
  "grant_type": "authorization_code",
  "code": "...",
  "redirect_uri": "..."
}
// Response:
{ "access_token": "...", "refresh_token": "...", "expires_in": 7200 }
    ⚠ Token accumulation cap: Starting January 2026, max 10 unrevoked tokens per user per app. HTTP 400 "too many unrevoked access tokens" means you must revoke old tokens via DELETE /v1/permissions then retry. Always revoke on user logout.

  6. Call the API

    GET /v1/workouts
Authorization: Bearer ACCESS_TOKEN

    Available resources: /v1/user, /v1/workouts, /v1/routes, /v1/plans, /v1/power_zones

    ⚠ No standalone HR / Recovery / Strain endpoints: These metrics are only available embedded inside workout_summary objects within /v1/workouts. See Section 6a.

6

Webhook Configuration (workout_summary events only)

POST /v1/webhooks
Authorization: Bearer <access_token>
{ "webhook_token": { "url": "https://your-app.com/wahoo/webhook" } }
⚠ Only workout_summary events are supported. Events such as heart_rate.updated, activity.completed, and recovery.updated are not Wahoo Cloud API webhook events.

Webhook Payload Example

{
  "event_type": "workout_summary",
  "user_id": "550e8400-...",
  "workout_summary": {
    "workout": {
      "id": 12345, "name": "Morning Run",
      "workout_summary": { "duration_in_seconds": 2700, "heart_rate_avg": 148 }
    }
  }
}
Payload ambiguity: Wahoo may use nested (workout_summary.workout.workout_summary) or flat (workout_summary) structure. Parse both defensively.

Requirements & Retry Policy

  • offline_data scope required
  • Endpoint must respond HTTP 200 within 30 seconds
  • Delivery is NOT exactly-once — duplicates are possible
  • Retry schedule: 30 min → 4 h → 24 h → 72 h (5 attempts then dropped)

Signature Verification

const hmac = crypto.createHmac('sha256', WEBHOOK_SECRET);
hmac.update(rawPayload);
const computed = hmac.digest('hex');
if (computed !== request.headers['x-wahoo-signature']) return 401;

Error Handling & Recovery

⚠ Refreshing a token does NOT immediately revoke the previous one. The old token is only invalidated after the first successful API call with the new token. Always refresh immediately before an API call — never speculatively.

Graceful Degradation

  • API Down? Display last-cached metrics with "stale data" badge
  • Partial Failure? Show available widgets; hide those that failed
  • Never log full tokens — log hashed/anonymized user IDs only

3. Limitations & Constraints

Items marked CORRECTED supersede v1.0. Items marked NEW were not in v1.0.

3a. Official API-Level Limitations

⏱️ Data Latency: Real-time HR is available <1 second via BLE directly from device — not via the Cloud REST API. Workout summaries appear in the Cloud API 1–5 minutes after device sync. Daily summaries finalize at midnight UTC. There is no live HR streaming through the REST API.
📊 Sampling Precision: HR accuracy ±2 BPM field / ±1 BPM lab. HRV accuracy ±5% (baseline dependent). Strain score is algorithm-derived, not directly measured.
📱 Offline Behavior: Strap stores last 7 days locally; syncs within 30 minutes of reconnection. Extended offline (>7 days) leads to data loss on strap.
🚦 Rate Limits CORRECTED
WindowSandboxProduction
Per 5 min25200
Per hour1001,000
Per day2505,000
Authentication, token refresh, and FIT-file downloads are exempt. v1.0 incorrectly stated "100/hr free, 1,000/day; $99/mo for 100,000/day". Correct production daily limit is 5,000. Access is approval-based, not subscription-based.
🔑 Token Accumulation Cap NEW CRITICAL

Starting January 1, 2026 each application is limited to 10 unrevoked tokens per user.

  • Access tokens expire 2 hours after issuance (expires_in: 7200)
  • Unrevoked tokens auto-deleted 60 days after creation
  • Critical: Refreshing a token does NOT revoke the previous one until the first successful API call with the new token is made. Refresh-without-call leaves both tokens active
  • Cap hit → OAuth callback returns HTTP 400 "too many unrevoked access tokens"
  • Mitigation: revoke via DELETE /v1/permissions on every logout; refresh immediately before API calls, not speculatively
🔧 Device Compatibility: Only Wahoo Gen 2 officially supported. Gen 1 has limited ECG functionality. Firmware <v2.0 may have API bugs.
🌍 Regional Restrictions: API available in North America and EU. Asia-Pacific limited (Singapore, Tokyo only). China/Russia not supported.
💾 Data Retention: Workout summaries retained for the lifetime of the account. Raw 1Hz HR samples are device-level only and not accessible via the Cloud API. No published retention policy for granular data.
🔐 Privacy & Consent: Requires explicit user consent per scope. GDPR-compliant data deletion available (30-day window).
💰 Access Model CORRECTED

API access is gated by approval, not purchased. All applications submit via the Wahoo API Agreement. Sandbox apps get 250 req/day. Production approval (at Wahoo's discretion) grants 5,000 req/day. v1.0 incorrectly described a "$99/month paid tier".

🔔 Webhook Event Types CORRECTED

Only workout_summary webhook events are officially supported. The events heart_rate.updated, activity.completed, and recovery.updated listed in v1.0 are not real Wahoo Cloud API events. Delivery is not exactly-once; duplicates are possible. Retry: 30 min → 4 h → 24 h → 72 h → dropped. The offline_data scope is required.

📋 Plan File Access Window NEW

Plan files are only retrievable 3 days before through 1 day after the workout's scheduled start time. Outside this window → no data returned. Requires active Wahoo subscription + plans_read scope. Plans scheduled >6 days out don't appear on ELEMNT devices.

🏃 Third-Party Workout Data Unavailable NEW

Wahoo does not share workout data originating from third-party applications (Zwift, Strava, TrainingPeaks, etc.) through its API. Only workouts recorded by Wahoo hardware or the Wahoo app are accessible via /v1/workouts.

🔢 Decimal Values Returned as Strings NEW

The Wahoo API returns certain decimal fields as JSON strings (e.g., "distance_accum": "8500.0" instead of 8500.0). Integrations must explicitly cast these to numbers before arithmetic — otherwise string concatenation silently produces wrong values.

🔒 Gated Production Access NEW

API is not openly available. All apps must submit through the Wahoo API Agreement and be approved. New apps start in sandbox. No self-serve upgrade path.

⚡ Webhook Latency: 2–10 second latency from device event to delivery. Events can arrive out-of-order when retries overlap with new events. Not suitable for ultra-low-latency use cases.
🔋 Battery & Connectivity: Continuous BLE sync reduces battery from 250h to ~40h. ANT+ only extends to 300h. No WiFi support.
🎯 Accuracy Degradation: HR accuracy drops with motion artifacts, poor chest contact, or high sweat. Use confidence score >0.85 as a reliability threshold.
📡 Wireless Interference: ANT+ on 2.4 GHz (shared with WiFi, BT). Crowded RF environments may cause data loss.
🔄 API Versioning: Currently v1. No documented backwards-compatibility guarantee. Contact Wahoo API Support via Zendesk for versioning questions.
🛠️ Support SLA: No SLA on API uptime. Status: status.wahooligan.com. Community support via forums.

6. Integration-Discovered Technical Limitations

Real-world constraints discovered while building this dashboard integration. These are not covered in official Wahoo documentation and represent practical engineering findings from the live codebase at backend/ and frontend/src/.

Severity: CRITICAL Functional blocker   HIGH Data integrity / security   MEDIUM Operational / UX   LOW Minor / edge-case

6a. Missing API Endpoints

Heart Rate, Recovery, and Strain Have No Standalone Cloud API Endpoints CRITICAL

The Wahoo Cloud API does not expose:

  • GET /v1/user/me/metrics/heart_rate — does not exist
  • GET /v1/user/me/metrics/recovery — does not exist
  • GET /v1/user/me/metrics/strain — does not exist
  • Any dedicated HRV history endpoint — does not exist

All such metrics are only available embedded inside workout_summary objects within GET /v1/workouts. On a rest day with no recorded workout, these metrics are inaccessible for that day.

Dashboard impact: In production (non-demo) mode, the Today's HR, Recovery, Strain, and HRV widgets are always empty unless the user completed a recorded workout that day. All demo mode data is synthetic.

Codebase: backend/services/wahoo_client.py — get_today_heart_rate(), get_today_recovery(), get_today_strain() all explicitly return None in real mode.

No HR Granularity via REST MEDIUM

Minute-by-minute or raw 1Hz HR data requires BLE streaming directly from the device — not available via Cloud REST. The API only surfaces per-workout aggregates (avg HR, max HR).

6b. Training Metrics Constraints

Power Meter Required for CTL / ATL / TSB — All Null Without One CRITICAL

Training Stress Score (TSS) — the input for Chronic Training Load (CTL), Acute Training Load (ATL), and Training Stress Balance (TSB/Form) — is only populated when the user has an ANT+ or BLE power meter connected during the workout. Without one, these fields are null:

  • workout_summary.power_bike_tss_last
  • workout_summary.power_bike_np_last
  • workout_summary.power_avg
  • workout_summary.work_accum

Impact: Users without a power meter see zeroed or "Calibrating" fitness/form metrics. CTL does not build. The Training Capacity gauge stays at 0.

Potential mitigation (not implemented): HR-based TSS (hrTSS) estimation requires the user's Lactate Threshold HR — not exposed by the Wahoo API, must be user-configured.

Codebase: backend/services/training_metrics.py, backend/services/wahoo_client.py:214–253

Demo Training Status Frozen at June 2024 MEDIUM

Synthetic TSS history is generated with random.Random(42) anchored to 2024-06-13. The "This Week" card always shows June 9–15, 2024 regardless of current date. Switching demo → real mode causes a sudden drop to zero CTL/ATL/TSB (no real TSS history).

Codebase: backend/services/training_metrics.py:18

Training Status Fetches 90 Days on Every Page Load — No Cache MEDIUM

The training-status endpoint fetches 90 days of workouts on every request (multiple paginated API calls), consuming a significant portion of the daily rate limit. No server-side caching exists for this computation.

Codebase: backend/routers/metrics.py:152

6c. OAuth & Token Management

Too Many Tokens Triggers Destructive Revoke-All (All Users Affected) CRITICAL

When the 10-token cap is hit, the current recovery strategy revokes and deletes all stored sessions — not just the triggering user's. This:

  • Forces all users in a multi-user deployment to re-authenticate
  • Is irreversible without re-auth
  • Breaks simultaneous multi-browser access

Proper fix (not yet implemented): Track tokens per wahoo_user_id; revoke only that user's old tokens.

Codebase: backend/routers/auth.py — _try_revoke_stored_sessions()

Token Refresh Is Reactive Only — No Proactive Expiry Check HIGH

Refresh triggers only on a 401. expires_at is stored per-session but never checked proactively. A user with a valid session cookie but a 2h-expired Wahoo token will hit silent failures on the first API call.

Codebase: backend/services/wahoo_client.py:54–67

CSRF OAuth State Expires After 15 Minutes — No User Feedback MEDIUM

The CSRF state is pruned after 15 minutes. A slow authorization flow returns "Invalid OAuth state" with no timeout explanation. Hardcoded; not configurable.

Codebase: backend/routers/auth.py:33–39

Token Revocation Returns No Success/Failure Signal MEDIUM

revoke_token() returns None on both success and failure. If the Wahoo API is down during logout, the user appears disconnected locally but the token remains active on Wahoo's servers until the 2h TTL or 60-day expiry.

Codebase: backend/services/wahoo_client.py:115–121

6d. Data Model & Normalization

Workout Pagination Silently Capped at 300 Items HIGH

Hardcoded maximum of 10 pages × 30 items = 300 workouts. Athletes who train twice daily can exceed 300 workouts in a 90-day window. Overflow is silently dropped with no warning in logs or response.

Codebase: backend/services/wahoo_client.py — _MAX_WORKOUT_PAGES = 10

Activity Normalization Permanently Drops GPS, Tags, and Raw Sensor Data MEDIUM

_normalize_activity() drops: workout.map_polyline (GPS), workout.tags (annotations), workout.samples (raw time-series). The /api/raw endpoint preserves the full payload; normalized workout views do not.

Codebase: backend/services/wahoo_client.py:214–253

Activity Type Derived From User-Editable Name, Not Canonical Type ID LOW

Type is set from workout.name (string, user-editable) instead of workout_type_family_id (integer). "Morning Run" and "Easy Run" appear as different activity types despite being the same workout type.

Codebase: backend/services/wahoo_client.py:237

HRV Field Required in Schema But May Be Absent in Real API Responses MEDIUM

HeartRateDailySummary.heart_rate_variability_rmssd is non-Optional in the Pydantic schema. If absent from a real response (workout too short for RMSSD, unsupported device), Pydantic raises 422 and the entire metrics response fails.

Codebase: backend/models/schemas.py:29–37

Power Zones Not Indexed by Activity Type MEDIUM

Wahoo supports per-activity-type FTP (cycling vs running) but the API returns a flat list with no query-by-type parameter. Users with multiple FTPs see all zones without a way to match zones to specific activities.

Codebase: backend/models/schemas.py:130–147

Recovery Status and Strain Zone Have No Enum Validation LOW

Both fields are plain strings with no enum constraint. If Wahoo changes label values, the frontend must handle them without breaking chart rendering.

Codebase: backend/models/schemas.py:42–56

6e. Webhook Reliability & Security

Webhook Signature Verification Optional — Unverified Events Marked as Verified HIGH

If WAHOO_WEBHOOK_SECRET is not set, any POST to /api/webhooks/wahoo is accepted without HMAC-SHA256 verification. Due to a logic flaw, events accepted without a configured secret are stored with "verified": true, making the flag unreliable for audit.

Fix: Always set WAHOO_WEBHOOK_SECRET in production. Return 401 (not 200) when no secret is configured.

Codebase: backend/routers/webhooks.py:100–106, 132

Webhook Payload Ambiguous — Two Delivery Structures Possible MEDIUM

Wahoo delivers payloads in two structures (nested workout_summary.workout.workout_summary vs flat workout_summary). Both are parsed defensively. A third format variant would silently produce None and drop the workout from the cache.

Codebase: backend/services/workout_event_cache.py:56–64

Replay Attack Window 5 Minutes With Lenient Timestamp Parsing MEDIUM

Timestamp validation uses a 5-minute window. If the timestamp field is present but unparseable, the request is silently allowed. If no timestamp is provided, the replay check is skipped entirely.

Codebase: backend/routers/webhooks.py:114–122

Webhook Event Log Silently Truncates at 500 Entries LOW

Events in backend/data/webhook_events.json are silently truncated to 500 when the limit is exceeded (oldest dropped). No alert, log, or metric is emitted at truncation time.

Codebase: backend/routers/webhooks.py:19, 56–57

Malformed Webhook Events Silently Dropped MEDIUM

Payloads missing either a workout id or starts timestamp are silently discarded with no error response and no log entry. The user must wait for the next scheduled poll.

Codebase: backend/services/workout_event_cache.py:62–64

6f. Storage & Operational Limitations

OAuth Tokens Stored Plaintext on Disk CRITICAL

Access tokens, refresh tokens, and expiry timestamps for all users are stored in plaintext JSON at backend/data/sessions.json. A server compromise, misconfigured filesystem permission, or backup leak exposes all user tokens — usable to call the Wahoo API on behalf of users without consent.

Production requirement: Encrypt tokens at rest (e.g., Fernet with an env-stored key, or a secrets manager like AWS Secrets Manager / HashiCorp Vault).

Codebase: backend/services/session_store.py:37–47

Demo Mode Auto-Activates Without Startup Logging MEDIUM

If either WAHOO_CLIENT_ID or WAHOO_CLIENT_SECRET is missing, demo mode activates silently — regardless of DEMO_MODE=false. No server startup log indicates which mode is active. A misconfigured credential causes real OAuth to be silently bypassed.

Codebase: backend/config.py:24–26

Admin "Connected Users" Counts Sessions, Not Unique Wahoo Users LOW

Connected-users count reflects active session cookies, not unique wahoo_user_id values. One user with 3 browser sessions shows as 3 connected users.

Codebase: backend/routers/admin.py:15

Rate Limit Display Defaults to 100/100 Before First API Call LOW

Before any API call in a fresh session, the admin panel shows hardcoded defaults (remaining: 100, limit: 100) which do not reflect actual sandbox limits (250/day) or prior-session consumption.

Codebase: backend/services/rate_limit_store.py:64–70

Rate Limit Headers Parsed Fragily With Silent Fallback LOW

Headers parsed with .split(",")[0].strip(); on any parse failure the code silently falls back to hardcoded defaults (95 remaining, 100 limit) with no log message.
